# ADR 0005: Independent reversal review and service work cycles

Status: accepted by the owner for Phase 1 Milestone 5 implementation. Governing specification: PRD v1.1, Sections 16.1–16.7; explicit owner decisions define these boundaries. This supersedes earlier reversal/reopen deferral, without changing Milestones 1–4.

Approved submitted values cannot be edited. Unprocessed APPROVED expenses and APPROVED leave strictly before the start date in the current organization timezone may enter REVERSAL_REVIEW. Requester or an eligible snapshotted final-step candidate initiates with an explicit withdraw/correct intent and reason. Neither requester nor initiator may decide. A different currently eligible final-step candidate accepts or denies; insufficient candidates leave review blocked. Admin or finance-processing authority alone is insufficient. Acceptance rechecks the boundary; denial remains possible after the leave boundary and restores the existing authorization without a new approval.

Review blocks expense processing immediately. REVERSED, COMPLETED expenses and CLOSED services are terminal. Source approval identity, policy, fields, approved_at, decisions and history remain immutable. An accepted correct-intent reversal permits the owner to create exactly one new linked DRAFT, copying tenant, requester, type, department, title, intake provenance and due_at. It requires new submission/approval identities under current policy and candidates. The terminal source receives only a distinct create_correction audit event.

Service RESOLVED can reopen to REOPENED, then start IN_PROGRESS and resolve again. Requester, current department manager or admin may reopen; the retained assignee must remain active, in the department and hold an active organization role. No reassignment or due-date reset occurs. Each new cycle needs separate immutable resolution before closure. The original resolution column stays historical; detail presents the current cycle's evidence and pending work has no current resolution.

Service reopening selects explicit immutable/versioned organization configuration after locking. The approved pilot duration is 604800 seconds (7 days), configured rather than hard-coded. Bounds are 3600 through 2592000 seconds; expiry is inclusive from the latest actual RESOLVED event. Missing/invalid policy conflicts. PostgreSQL time is sampled after request locking; commit guards also reject backdated expiry or leave-date bypass.

Append-only reversal requests, decisions, correction links, service resolutions, reopenings and policy records bind tenant-qualified events, current submission/cycle identities and guarded pointers. Existing advisory idempotency keys and request row locks serialize mutations. Durable receipt outcomes survive delayed retries; current authentication and visibility are rechecked, and returned detail may reflect newer state. No extra event, plan, decision, resolution or child is created on retry.

The additive migration does no historical backfill. Lazy capture of original managed approvals/resolutions requires consistent existing trusted actor, time, fields, policy, candidates and events, recording the real capture actor/time separately. Incomplete evidence conflicts without writes. Legacy unvalidated records cannot enter new lifecycle paths. Downgrade refuses to discard lifecycle evidence; unused added PostgreSQL enum labels remain on an otherwise safe downgrade.

Sensitive reads retain current participant and active-role audit scopes. Admin alone receives no expense/leave access. Finance can see an approved expense held for reversal to explain why processing is blocked, but this grants no reversal decision authority. Linked drafts are independently authorized; source visibility never grants child access. Reversal queues exclude requester, initiator and ineligible candidates before pagination.

Non-goals: refunds/financial adjustments, actual payments, payroll/calendar undo, completed-expense correction, retrospective leave reversal, closed-service reopen, delegation/reassignment, service clarification, AI, notifications, frontend UI, analytics/SLA, deployment and Phase 2 async/outbox work. No new dependencies or authentication changes.
